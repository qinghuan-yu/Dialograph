# Dialograph

Dialograph 用于对用户自愿提供的本地 JSON 对话数据进行结构化分析，帮助用户理解沟通模式、关系动态、人物印象与互动边界。

它的核心目标不是“获取聊天记录”，而是：

> 把已有对话材料结构化成可分析的关系档案。

## 输入、过程、输出

输入：

- 用户已经拥有、并自愿放入本地工作区的 JSON 对话数据。

过程：

- 自动提取有效消息
- 清洗系统消息、空内容和异常时间字段
- 按时间排序和分段
- 建立长期会话与阶段统计
- 对长对话进行分块阅读和证据抽取
- 汇总关系信号、人物信号、反证与存疑
- 生成结构化报告

输出：

- 关系动态
- 人物印象
- 互动模式
- 证据片段
- 复盘报告
- 可用于后续检索/RAG 的结构化证据档案

## 适用场景

- 复盘长期沟通模式
- 理解一段关系中的互动节奏与边界
- 梳理对方在对话中呈现出的稳定表达风格
- 识别长期重复出现的支持、回避、协作、冲突和修复模式
- 将零散聊天记录整理成可追溯的证据化分析材料

## 边界与伦理

本项目用于对用户自愿提供的聊天记录进行结构化分析。

本项目不鼓励、不支持在未经同意的情况下分析他人隐私数据，也不用于冒充、操控、监视、骚扰、画像攻击或替代真实关系沟通。

分析结果只应被视为基于文本证据的辅助理解，而不是对任何人的本质判断、医学诊断或关系裁决。

## 工作流概览

1. 将已有 JSON 对话文件放入 `talks/`。
2. 运行完整工作流。
3. 系统生成预处理统计、全量覆盖说明、分块证据、结构化证据总表、关系分析报告和人物侧写报告。

## 运行方式

### 本地网页

在项目根目录启动：

```bash
python agent/web_app.py
```

浏览器打开 http://127.0.0.1:5173 。可选择 `talks/` 中的对话或导入 WeFlow JSON，运行仅预处理或完整分析，查看真实阶段、分块进度和统计图表，并阅读、下载报告与证据。完整分析使用上方 `.env` 配置的模型服务。

网页任务支持停止与继续；输入快照、状态和输出保存在被忽略的 `analysis/web_jobs/{job_id}/` 中。网页任务不会覆盖原有命令行报告。格式要求、输出与验证说明见 [前端说明](frontend/README.md)。

网页与命令行使用同一份 WeFlow 私聊输入校验：缺少发送者归属、`text/image` 等非 WeFlow 类型约定、明确的群聊标记或同一方出现多个稳定账号时会拒绝分析。缺少账号字段的导出只能依据提供的 `isSend` 判断归属，请确认输入确实是两人私聊。

### 命令行

推荐直接运行完整工作流：

常用命令：

```bash
python agent/run_workflow.py
```

只处理某个对象：

```bash
python agent/run_workflow.py 名称关键词
```

重跑全部分析：

```bash
python agent/run_workflow.py --force
```

补/重跑人物侧写：

```bash
python agent/run_workflow.py 名称关键词 --force-persona
```

调整分块大小：

```bash
python agent/run_workflow.py --chunk-size 900 --chunk-max-bytes 18000 --chunk-max-prompt-bytes 32000
```

默认单块原文上限为 `18000` 字节，并额外按实际提示词大小控制在约 `32000` 字节内。分块阶段只要求模型输出紧凑、合法的 JSON 证据对象，不再要求每块生成长篇 Markdown 分析，以降低 `max_tokens` 截断、格式跑偏和远端断连概率。分块请求默认使用 `--chunk-timeout 180`，新分块成功后默认按 `--chunk-sleep 1.0` 做轻微冷却；阶段总结、最终报告和人物侧写仍使用全局 `--timeout`。只有分块阶段遇到远端连接断开、超时、`413` 等可恢复错误时，工作流才会自动缩小分块和提示词预算，并为当前对象重跑一次新的 run，降低长对话首块过大导致的失败概率；最终报告阶段失败不会触发重新分块。如需关闭该行为，可加 `--no-auto-shrink`，如需关闭分块冷却可加 `--chunk-sleep 0`。

从未完成的 run 继续：

```bash
python agent/run_workflow.py 名称关键词 --resume-run 20260529-153000
```

续跑会恢复该 run 保存的分块参数，并验证输入、解析/分析流程、模型与服务指纹、覆盖清单和缓存消息范围。输入或流程改变、旧 run 缺少校验信息时会明确拒绝复用；此时请去掉 `--resume-run` 新建运行。新 run ID 含随机后缀，请使用实际目录名。成功运行也会保留恢复参数与指纹。

如果只想生成预处理统计和 prompt，可以运行：

```bash
python agent/run_analysis.py <编号或名称>
```

Windows 下也可以双击根目录的：

```text
一键运行全部分析.bat
```

这个批处理保留已有 `analysis/`、缓存和网页任务历史，处理 `talks/` 下全部 JSON 文件，仅跳过完整且输入、流程、提示和模型指纹一致的产物。关系报告重做时同步更新人物侧写；旧产物缺少指纹会重新生成。也可在命令行显式使用 `--force`。

正式关系报告发布前会审计并暂存完整产物，再替换兼容路径；发生异常时恢复旧文件和目录，最后才更新结果指针。这不保证断电或强制结束进程时的事务性；同一对象请串行运行。

两个 `run_single_pass_*.py` 是采样预览入口，结果与中间文件只写入 `analysis/预览/`，报告头含预览说明。人物预览读取同目录下的关系预览；这些文件不替代完整工作流的正式报告。

运行单元测试：

```bash
python -m unittest discover -s tests -v
```

审计已有分析产物完整性：

```bash
python agent/artifact_audit.py
```

只审计某个对象：

```bash
python agent/artifact_audit.py 示例对象
```

## 工作流链路

完整链路如下：

```text
talks/*.json
  -> 原始消息读取
  -> 消息解析与诊断
  -> 时间排序与异常字段标记
  -> 统计建模
  -> 长期会话建模
  -> 全量文本导出
  -> 连续分块
     -> 按实际提示词字节预算二次切分
  -> 每块 LLM 证据分析
     -> 可恢复请求失败时自动缩小分块并重跑当前对象
  -> 每块结构化 JSON 证据抽取
  -> 分块覆盖清单
  -> 阶段总结
     -> 按实际提示词字节预算动态压缩合并
  -> 结构化证据总表
  -> 结构化证据摘要
  -> 关系动态分析报告
  -> 人物印象/表达风格侧写报告
```

### 1. 消息解析与清洗

系统会从 JSON 中提取有效消息，并记录解析诊断：

- 原始消息数
- 有效解析消息数
- 跳过消息数与跳过原因
- 是否发生时间重排序
- 时间格式异常数量
- 时间戳异常数量

系统消息、空内容和无法分析的记录不会直接进入最终建模，但会被计入诊断文件。

### 2. 时间排序与长期会话建模

解析后的消息会按时间戳排序，并保留原始顺序索引。

统计中包含 4 小时间隔切分的会话指标：

- 会话总数
- 会话发起者
- 会话收尾者
- 会话消息数
- 会话时长
- 会话内回复速度

这些指标用于辅助理解互动节奏，而不是单独决定关系类型。

### 3. 全量分块阅读

长聊天不会一次性塞进最终 prompt。系统会按时间顺序将全部有效消息切成连续分块：

- 每个分块包含一段连续原文
- 每个分块由 LLM 独立阅读并抽取紧凑证据
- 每个分块产出结构化 JSON 证据对象，避免中间层生成过长散文
- 分块覆盖清单用于核对是否覆盖全部有效消息

因此完整工作流保证的是“LLM 逐块读完整段对话”，不是“最后一步单 prompt 直接读完整原文”。

### 4. 阶段总结与结构化证据

分块分析会合并为阶段总结；结构化证据会合并为证据总表和摘要。

结构化证据包含：

- `events`：事件层证据
- `relation_signals`：关系模型支持/反证信号
- `persona_signals`：人物印象/表达风格建模信号
- `counter_evidence`：反证与边界条件
- `uncertainties`：仍不能判断的问题

证据必须包含上述五个列表，条目需满足字段和枚举约定；裸 `{}`、错误类型或缺失条目字段会重试或失败。合法的全空列表标记为 `evidence_status=insufficient`，允许模型保留“没有足够信号”。这些检查验证结构，不证明引文或推断在语义上正确。

每类结构化摘要最多选取 60 条，按分块轮询；块数超过预算时覆盖时间轴。摘要显示总数、入选数和省略数，完整条目仍保留在证据总表。覆盖缩减会出现在审计提示和网页运行日志中；逐块读取全部消息不等于最终报告保留全部细节。

### 5. 最终报告

最终报告基于：

- 统计摘要
- 解析诊断
- 全量覆盖说明
- 结构化证据摘要
- 阶段总结
- 已生成的关系分析报告

输出分为两个主报告：

- `分析_{对象名}.md`
- `人物侧写_{对象名}.md`

### 6. Run 管理与失败恢复

完整工作流会先把本次运行写入：

```text
analysis/临时文件/{对象名}/runs/{run_id}/
```

只有当关系分析成功生成后，才会把本次 run 的分块、结构化证据、阶段总结和关系报告同步到旧的兼容路径。这样中途失败不会破坏上一次成功结果。

每个成功 run 会更新：

```text
analysis/临时文件/{对象名}/latest_run.json
```

如果某次运行在分块阶段中断，可以使用 `--resume-run {run_id}` 复用该 run 中已经完成的 `chunk_*.md` 和 `evidence_*.json`，继续后续分块与最终报告生成。

如果失败来自单个分块 prompt 过大，推荐直接重新运行原命令。默认开启的自动缩块会在可恢复错误后改用更小分块和更小提示词预算创建新的 run；已经成功完成过的旧结果仍会保留，只有新 run 成功后才会同步到兼容路径。

阶段总结过长时，工作流会按实际合并 prompt 字节数动态切批，并在每个批次开始和完成时打印进度。合并批次会复用上一批成功时学到的输出上限，避免每批都从最小 `max_tokens` 重新试探。

工作流会校验模型输出完整性：分块必须包含可解析的结构化 JSON；阶段总结、关系报告和人物侧写必须包含完成标记。最终报告 prompt 会按统计、覆盖、证据摘要和阶段总结分别限长，避免在最后一步重新塞入过大的上下文。缺少这些条件时不会把文件当作成功产物复用，避免网络中断或 `max_tokens` 截断造成的残缺报告继续污染后续分析。

阶段总结合并批次会缓存到当前 run 的 `merge_batches/round_*/batch_*.md`。如果网络在合并阶段中断，下次 `--resume-run` 会复用已经完成且带完成标记的合并批次，只重跑缺失或不完整的批次。

## 输出位置

生成结果默认写入 `analysis/`：

- `分析_{对象名}.md`：关系动态与互动模式分析
- `人物侧写_{对象名}.md`：人物印象与表达风格建模
- `临时文件/{对象名}/预处理_{对象名}.txt`：统计摘要和代表性片段
- `临时文件/{对象名}/全量解析_{对象名}.txt`：完整解析后的全部有效消息
- `临时文件/{对象名}/统计_{对象名}.json`：结构化统计结果
- `临时文件/{对象名}/解析诊断_{对象名}.json/.md`：解析诊断
- `临时文件/{对象名}/分块分析/chunk_*.md`：每个连续分块的紧凑 JSON 证据响应
- `临时文件/{对象名}/结构化证据/evidence_*.json`：每个分块的结构化证据
- `临时文件/{对象名}/结构化证据总表_{对象名}.json`：结构化证据档案
- `临时文件/{对象名}/分块覆盖清单_{对象名}.json`：全量读取覆盖校验
- `临时文件/{对象名}/阶段总结_{对象名}.md`：中间证据总结
- `临时文件/{对象名}/结构化证据摘要_{对象名}.md`：最终报告使用的证据摘要
- `临时文件/{对象名}/runs/{run_id}/`：单次运行的完整中间产物
- `临时文件/{对象名}/latest_run.json`：最近一次成功提升的 run 指针

`talks/` 和 `analysis/` 默认被 `.gitignore` 忽略，以避免把私人对话和分析产物提交到版本库。

## 结构化证据与 RAG

`结构化证据总表_{对象名}.json` 是后续做 RAG 的主要入口。

后续可以把这些条目导入 SQLite/FTS 或向量库，按以下维度检索：

- 时间范围
- 关系模型
- 人物特征
- 互动类型
- 反证类型
- 存疑问题

## 分析原则

- 不预设对方性别、性取向、关系目标或恋爱/暧昧前提
- 所有判断必须引用聊天记录具体证据
- 严格区分事实、推断、假设和存疑
- 优先寻找反证
- 不迎合、不放大、不诊断
- 分析结果只作为辅助理解，不替代真实沟通
