验收对象是固定命题下的证据角色和实际提供的材料范围。工具不调用模型，不根据关键词自动判断一段聊天的含义，也不作为报告发布时的通用语义裁判。

## 案例

公开案例位于 `tests/fixtures/claim_semantic_cases.json`，包含13个独立编写的合成场景：关心与时间限制、明确拒绝、外传与补救、补救结果未知、初始简短回复与后续支持、说话人归属、复制文本、第三人话语、第一人称自述、局部照片边界、延期与完成、群体活动边界及继续相处。

每个案例记录固定命题、源消息、必需的过程位置、人工判断和候选消息的角色。角色按当前命题判定：

| 角色 | 含义 |
| --- | --- |
| `support` | 支持当前命题 |
| `counter` | 直接削弱或反驳当前命题 |
| `limitation` | 限定适用的时间、场景、条件或可推断程度 |
| `irrelevant` | 不能用于支持或反驳当前命题；不表示这条消息没有其他价值 |

例如，“没去教室”对“当时在教室”是反证；对“已经答应帮忙”则只是条件信息，不能代替明确的答应或拒绝。转述第三人的话也不同于第一人称复述自己的经历：后者可以支持“对方如此自述”，仍不能核实外部结果。

真实会话案例、逐字原文和来源哈希只保存在被忽略的 `analysis/`。人工标注首版需要后续独立复核；合成标注自检通过不代表模型达到同样的正确率。

## 输入与运行

预测文件结构如下，`predictions` 应为整套案例各提供一项：

```json
{
  "schema_version": "claim-semantic-predictions-v1",
  "predictions": [
    {
      "case_id": "care_and_busy_schedule",
      "proposition": "对方在这次交流中表达了关心。",
      "assessment": "supported",
      "roles": {"2": "support", "3": "limitation"},
      "available_positions": [1, 2, 3]
    }
  ]
}
```

`assessment` 为 `supported`、`contradicted` 或 `insufficient`。命题须与案例原文一致；若修改命题，须先重新人工标注，不能沿用旧角色。缺失案例计失败，重复或未知案例编号拒绝，不能只选成功样本。

`available_positions` 应由运行器从实际发送的原文记录，不根据模型自述或期望窗口推算。工具检查提供的记录与必需过程位置是否一致，无法独立证明记录对应真实请求，亦不证明模型已认真阅读。

```powershell
python agent/evaluate_claim_semantics.py --cases tests/fixtures/claim_semantic_cases.json --predictions analysis/semantic_predictions.json --output analysis/semantic_evaluation.json
```

退出码0表示全部检查通过，1表示存在不一致。结果按命题、判断、证据角色和材料覆盖分别列出失败项及缺失位置；`general_semantic_correctness=not_evaluated` 表示没有评估任意自由成文报告的总体语义正确性。

测试工具本身：

```powershell
python -m unittest discover -s tests -p test_claim_semantics.py
```

测试包括：把取消见面误分为关心的反证、删掉后续回应、换命题、漏案例及CLI退出码。这些是验收机制与结论协议的回归，不是模型实测。
